# SOL-174 — One "Gastos do mês" on Mês, Meu ano and Para onde vai

Bug, high. Source: usability audit finding H (`docs/research/2026-11-14-usability-audit.md`, line 69). The owner's November 2026 shows three spending totals: Mês "Saídas R$ 3.050,50", Meu ano "Novembro R$ 3.321,50", Para onde vai "Total de saídas R$ 3.821,50" with Economia at 13,1% "das despesas".

Arithmetic of the owner's numbers: 3.821,50 − 3.321,50 = 500,00 = the Economia deposits (500,00 / 3.821,50 = 13,1%). 3.321,50 − 3.050,50 = 271,00 = card purchases of November − (fatura payments + deposits) of November. Each screen sums a different set of entries.

There is no shared definition. Each screen has its own SQL filter or fold, and D31 accepted the Mês difference as a trade-off (`docs/specs/decisions.md:257`).

## 2. The rule

**Gastos do mês** = the amounts of the entries dated in the month, on or after the opening date, that are a Saída or a Diário, **except** Saídas under Economia (Economia itself or a cofrinho) and fatura payments. A card purchase counts on its own date. This is D31's `Gastos`, now used by every screen and every month. **Guardado no mês** = Economia deposits − resgates in the same month (today's `savings.saved` / `totals.saved`). It is never part of Gastos and never a share of Gastos.

The server computes both in one pure rule in `domain.rs` that every slice calls (months, reports year, reports categories), so the three SQL filters collapse to one predicate. The web never adds or subtracts to get either figure.

Household impact: one number per month. Otherwise the user trusts none of them and plans with whichever is smallest.

Household impact of the four contested rows, one line each:

- Row 7: a purchase on the card lands in the month it was made, or the user thinks October was cheap and November expensive because of a bank calendar.
- Row 9: the fatura is not spent twice, or one purchase reads as two.
- Row 12: money moved to a cofrinho is still the user's, or saving looks like overspending and the saving rate punishes the habit Soldi wants.
- Row 16: the previsto is a plan, never spending, or the month shows money gone that the user never spent.

## 3. What each screen shows

For any month, the three screens show **the same Gastos and the same Guardado**. Two figures are intentionally different and keep their own labels, because they follow the bank account, not the month's consumption:

- `Saldo hoje` and `Projetado no fim do mês` move on payment dates (a card purchase drops them on the fatura's due date, D28), and `Projetado` includes unpaid contas, unpaid faturas and the Diário previsto.
- The Modo planilha columns `Saída` and `Diário` (D48) are the day-by-day cash ledger. They are columns, never a total called Gastos.

## 4. Edge cases

| Case | Expected |
|---|---|
| Card purchase on Dec 28, fatura paid on Jan 12 | Dec Gastos counts it; Jan Gastos does not count the payment; the year boundary changes nothing. |
| Conta with due day 31 in February | It falls due on Feb 28 (29 in a leap year). When paid in February it counts in February's Gastos; when unpaid it lands in the projection on Feb 28 or today, whichever is later. |
| Income and a conta on the same day | Independent: the conta counts in Gastos, the income in Entradas; the day's balance nets both. |
| Zero-income month | Gastos shown; `Comprometido`, the sentence's percentage and the saving rate are absent (division by zero is undefined, never 0% or 100%); `Resultado` = − Gastos − Guardado. |
| Negative opening balance | No effect on Gastos or Guardado; only Saldo and Projetado start below zero. |
| Fatura paid in a later month than its due month | The payment never counts in Gastos anyway; the purchases stay in their own months. |
| Month before the opening month | Refused as today (`month-before-opening`); Para onde vai also drops entries dated before the opening date (today it counts them). |

## 6. D-entry draft (for `docs/specs/decisions.md`; amends D31, keeps D28 and D49)

**D54 — One Gastos for every month; Guardado apart (2026-11-25, SOL-174).** `Gastos` (D31's definition: Saídas except Economia deposits and fatura payments, plus every Diário with card purchases on their own date, entries from the opening date on) is the only spending figure on Mês, Meu ano and Para onde vai, computed by one server rule. `Guardado` = deposits − resgates, shown apart and never a share of Gastos. The rule and its fold:

```rust
/// What an entry is to its month (D54).
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Flow { Income, Spent, Saved, Withdrawn, Ignored }

impl CategorySum {
    pub fn flow(&self) -> Flow {
        match self.kind {
            _ if self.fatura_payment => Flow::Ignored,
            CategoryKind::Bill if self.savings || self.cofrinho => Flow::Saved,
            _ if self.cofrinho => Flow::Withdrawn,
            CategoryKind::Income => Flow::Income,
            CategoryKind::Bill | CategoryKind::Daily => Flow::Spent,
        }
    }
}

/// Entradas (resgates out), Gastos and Guardado (deposits − resgates) of `sums` (D54).
#[derive(Debug, Default, Clone, Copy, PartialEq, Eq)]
pub struct Spending { pub income: Decimal, pub spent: Decimal, pub saved: Decimal }

pub fn spending<'a>(sums: impl IntoIterator<Item = &'a CategorySum>) -> Spending {
    let mut total = Spending::default();
    for sum in sums {
        match sum.flow() {
            Flow::Income => total.income += sum.amount,
            Flow::Spent => total.spent += sum.amount,
            Flow::Saved => total.saved += sum.amount,
            Flow::Withdrawn => total.saved -= sum.amount,
            Flow::Ignored => {}
        }
    }
    total
}
```

Task B adds the one mapping to the DTO:

```rust
impl Spending {
    pub fn totals(self) -> Totals {
        Totals { income: self.income, spent: self.spent, saved: self.saved,
                 performance: self.income - self.spent - self.saved }
    }
}
```

### 7.2 The one query

`reports::repo::category_sums(conn, user_id, from, to)` (reports/repo.rs:10-36), rewritten. It filters only `user_id` and the date range; every other cut is the rule. Callers pass `from` already cut at the opening date.

```sql
SELECT c.id AS category_id, c.name, c.icon, c.color, t.kind AS "kind: CategoryKind",
       date_trunc('month', t.date::timestamp)::date AS "month!",
       SUM(t.amount) AS "amount!", c.parent_id,
       COALESCE(p.name, c.name) AS "group_name!", COALESCE(p.icon, c.icon) AS "group_icon!",
       COALESCE(p.color, c.color) AS "group_color!",
       COALESCE(p.kind, c.kind) AS "group_kind!: CategoryKind",
       t.card_id, card.name AS "card_name?",
       (c.is_savings OR COALESCE(p.is_savings, false)) AS "savings!",
       t.cofrinho_id IS NOT NULL AS "cofrinho!",
       b.closing_day IS NOT NULL AS "fatura_payment!"
FROM transactions t JOIN categories c ON c.user_id = t.user_id AND c.id = t.category_id
LEFT JOIN categories p ON p.user_id = c.user_id AND p.id = c.parent_id
LEFT JOIN recurring_bills b ON b.user_id = t.user_id AND b.id = t.recurring_bill_id
LEFT JOIN recurring_bills card ON card.user_id = t.user_id AND card.id = t.card_id
WHERE t.user_id = $1 AND t.date BETWEEN $2 AND $3
GROUP BY c.id, p.id, date_trunc('month', t.date::timestamp), t.kind, t.card_id, card.name,
         t.cofrinho_id IS NOT NULL, b.closing_day IS NOT NULL
```
