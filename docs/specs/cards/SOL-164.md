# SOL-164 — Diário previsto

Owner, 2026-11-23: "Projected balances count no future daily spending (D16), so a future month reads greener than it will be. Add an opt-in estimate the person can turn on or off at any time; when on, each future day takes it as 'Diário previsto' in both views (lista and modo planilha) and in Próximos meses. Panel decides: a fixed value the person sets vs suggested from recent months and editable, where the switch lives, how a previsto is told apart from a real entry. Amends D16 (a declared number, never a silent average)."

## Money rules

Finance panel, 2026-11-23. Read: D16, D17, D28, D44–D48, `forecast/02-finance.md` §6 (4-0 "ignore", now overridden by the owner with an opt-in declared number), SOL-163; code `months/domain.rs` (`flows_by_day` :308, `month_view` :335, `forecast` :501), `soldi-types` `Day`, `Settings`.

Code facts the rules lean on:

- `Day.balance` already includes typed future rows; `projected_balance = balance − pending` (unpaid contas landed, D17). The estimate joins `pending`'s side only.
- `flows_by_day` drops card spends (D28), so `Flows.daily` is exactly the Diário that leaves the account on its own day.
- Month view, forecast, Próximos meses (lowest `ForecastDay` per month), RedDayAlert (`projected_tier` of `is_today || is_future` days) and Posso comprar (`withDraft` over `/api/forecast`) all read `projected_*`. One rule in the domain reaches all of them.

### R — rule table

Notation: `e` = saved estimate; `on` = flag; `T` = today (São Paulo, D13); `O` = `opening_date`; `daily(d)` = `Flows.daily` of `d` (non-card Diário typed for `d`).

| Id | Rule |
|---|---|
| R1 | `previsto(d) = if on && d > T && d ≥ O { max(e − daily(d), 0) } else { 0 }`. |
| R2 | `estimated(d) = Σ previsto(x)` for `x` in `[max(T+1, O), d]`, across month and year boundaries. |
| R3 | `Day.projected_balance(d) = balance(d) − pending(d) − estimated(d)`; `projected_tier` = `tier()` of that. `pending` is D17's, unchanged. |
| R4 | `Day.balance`, `Day.tier`, `Day.income/withdrawn/bills/daily` never change. `previsto(d)` is exposed apart (architect names the field). |
| R5 | `MonthView.projected_balance` (current and future month) = last day's R3 value. Past month: unchanged formula, no estimate (no day `> T`). |
| R6 | `MonthView.balance_today`, `balance_today_tier`, `totals.*`, `savings.*`: unchanged. |
| R7 | `ForecastDay.projected_balance(d)` = R3 for every day `max(T, O)..=horizon_end(T)`. For every date present in both, month view and forecast agree to the cent. |
| R8 | Planilha identity holds with the estimate: `Saldo(d) = Saldo(d−1) + Entrada − Saída − Diário − previsto(d)` inside a month (SOL-163 A5 extended). |
| R9 | Off (`on = false`, or no value saved): every number equals today's D16 output; existing tests pass unchanged. |
| R10 | The estimate never writes a row (D8), never appears in transactions, Totals, Meu ano, Para onde vai, Economia, CardFatura (`ahead` included). |

R-W — where it counts:

| Figure | Counts? | Why |
|---|---|---|
| `Day.projected_balance` / `projected_tier`, future days | yes | the card's point |
| same, today and past days | no | today is being typed; the past is real |
| `Day.balance` / `tier` | no | real money (R4) |
| `MonthView.projected_balance` (hero "Projetado") | yes, current and future months | end-of-month plan |
| `MonthView.balance_today` | no | real |
| `Totals` (income, bills, daily, outflow, performance, saved, withdrawn) | no | "Desempenho" is what was typed; mixing an estimate in makes a future month's performance look already lost |
| `savings` (`saved`, `rate_pct`) | no | the estimate is spending, not saving; zero-income month stays `rate_pct = null` |
| `/api/forecast` days | yes, `d > T` | Próximos meses and Posso comprar read it |
| Próximos meses (lowest per month) | yes | owner asked |
| RedDayAlert (first red day, lowest point) | yes; cause may be "Diário previsto" | the red is real if the person spends as declared |
| Posso comprar | yes, when on | *without it, "pode comprar" ignores the daily spending that will eat the same money* |
| CardFatura, Meu ano, Para onde vai, Economia, reports | no | real or committed only |

R-V — value and rounding:

| Input (`e`) | Result |
|---|---|
| `"50"`, `"50.00"`, `"0.01"`, `"10000.00"` | accepted, stored `NUMERIC(12,2)` as `50.00` … `10000.00` |
| `"0"`, `"0.00"`, `"-5.00"` | 422 `validation` (off is the switch, not a zero) |
| `"0.001"`, `"50.005"` | 422 `validation` (more than 2 places; same as other money input) |
| `"10000.01"` | 422 `validation` |
| `on = true` with no value saved | 422 `validation` |
| value `null` (cleared) | forces `on = false` |
| any walk sum | exact Decimal, no rounding (cents − cents) |

R-S — suggestion (pre-fill only):

| Id | Rule |
|---|---|
| R-S1 | Window = the 3 calendar months before `T`'s month, cut to days `≥ O`. Current month never. |
| R-S2 | Numerator = Σ Diário entries in the window with no card (`card_id` null or not a card); Saídas, income, resgates out. |
| R-S3 | `days` = calendar days in the window `≥ O`. No suggestion when `days < 28` or numerator = 0 (empty field, the person types). |
| R-S4 | Suggestion = `round_half_even(numerator / days, 2)`. |
| R-S5 | Never stored, never applied: becomes `e` only when the person saves it. Saved `e` is never recomputed. |

R-E — edge cases:

| Case | Rule |
|---|---|
| Month boundary | `estimated` carries into the next month's first day (R2); month view of M starts with the previsto of every future day before M. |
| Year boundary | same; Dec 31 → Jan 1 continuous. |
| Leap year | per calendar day; Feb 2028 has 29 previstos when all are future. |
| Due day 31 / clamps | untouched (D17); the estimate has no due day. |
| `O > T` | no previsto before `O`; `O` itself and later get it. |
| `T` = last day of month | that month's `projected_balance` has no estimate; next month day 1 = one previsto. |
| Past month | never. |
| Midnight (São Paulo) | yesterday's previsto vanishes; that day's real entries rule (D13). |
| Future typed cash Diário ≥ `e` | `previsto = 0`, never negative. |
| Future card Diário | does not fill the cap; its fatura lands on its due date (D28). |
| Future Saída / income | no effect on `previsto`; they move `balance` as today. |
| Negative opening balance | estimate subtracts the same; tiers as usual. |
| Month view beyond `horizon_end` | estimate still applies to every future day (no cliff); forecast stops at `horizon_end`. |
| Currency | `e` is in `settings.currency`, like every amount; changing currency converts nothing. |

### D16 amendment (draft for `decisions.md`)

D16's "future daily spending is not averaged in" stays the default. Opt-in (SOL-164): the person declares a per-day "Diário previsto" (`0.01..=10000.00`, settings, per user); when on, every future day on or after the opening date takes `max(estimate − typed cash Diário, 0)` in `projected_*`, month end, forecast, Próximos meses, RedDayAlert and Posso comprar; never in `balance`, Totals, savings or reports. Soldi may pre-fill a suggestion (3 complete months of non-card Diário ÷ days, half-even), applied only when saved, never recomputed. Card spends stay in faturas (D28). Off = D16 exactly.

### Domain (one shared rule)

`months/domain.rs`, next to `landing` (:290):

```rust
/// SOL-164 R1: what the Diário previsto adds on `date`, on top of the cash `daily` typed for it.
pub fn previsto_on(settings: &Settings, today: NaiveDate, date: NaiveDate, daily: Decimal) -> Decimal {
    match settings.daily_estimate {
        Some(estimate)
            if settings.daily_estimate_on && date > today && date >= settings.opening_date =>
        {
            (estimate - daily).max(Decimal::ZERO)
        }
        _ => Decimal::ZERO,
    }
}

/// R2: the previstos of the days before `from`.
fn estimated_before(
    settings: &Settings,
    today: NaiveDate,
    flows: &BTreeMap<NaiveDate, Flows>,
    from: NaiveDate,
) -> Decimal {
    if !settings.daily_estimate_on {
        return Decimal::ZERO;
    }
    let start = today.succ_opt().unwrap_or(today).max(settings.opening_date);
    start
        .iter_days()
        .take_while(|date| *date < from)
        .map(|date| previsto_on(settings, today, date, flows.get(&date).map_or(Decimal::ZERO, |flow| flow.daily)))
        .sum()
}
```

```rust
/// R-S1, R-S3: the 3 calendar months before today's, from the opening date; none under 28 days.
pub fn suggestion_window(today: NaiveDate, opening: NaiveDate) -> Option<(NaiveDate, NaiveDate)> {
    let month = first_of(today);
    let from = month.checked_sub_months(Months::new(3))?.max(opening);
    let to = month.pred_opt()?;
    ((to - from).num_days() + 1 >= 28).then_some((from, to))
}

/// R-S2..R-S4: the window's cash Diário per day, half-even; none when it could not be saved.
pub fn suggest(total: Decimal, from: NaiveDate, to: NaiveDate) -> Option<DailyEstimateSuggestion> {
    let days = Decimal::from((to - from).num_days() + 1);
    let amount = (total / days).round_dp_with_strategy(2, RoundingStrategy::MidpointNearestEven);
    check_estimate(amount).ok().map(|amount| DailyEstimateSuggestion { amount, from, to })
}
```

`check_estimate` (also used by `apply`): `value < Decimal::new(1, 2) || value > Decimal::new(1_000_000, 2) || value.normalize().scale() > 2` → `AppError::invalid("daily_estimate", …)`.

### Performance

- Month view and forecast: no new query (settings row already read). Walk cost +1 Decimal op a day; `estimated_before` loops days from tomorrow to the month's start only when on (≤ ~27k for a 2100 view, microseconds). Off returns at once.
- Forecast horizon unchanged: `horizon_end(today)`, 12 months. 4 queries as today.
- Suggestion: 2 queries. The SUM:

```sql
SELECT COALESCE(SUM(t.amount), 0) AS "total!"
FROM transactions t
LEFT JOIN recurring_bills b ON b.user_id = t.user_id AND b.id = t.card_id
WHERE t.user_id = $1 AND t.kind = 'daily' AND t.date BETWEEN $2 AND $3
  AND b.closing_day IS NULL
```

  Range scan on `transactions_user_date_idx (user_id, date)` for ≤ 92 days of one user; the join is a PK probe only for rows with `card_id`. `closing_day IS NULL` keeps cash and card ids that are not cards, exactly like `flows_by_day` (`d28_a_card_id_without_a_card_counts_on_its_date`). No new index.
- The suggestion GET does not call `extend_open_series` (a GET that writes is avoided; past series rows were written when Mês was opened).

## D49 — An opt-in, declared Diário previsto counts in the projection (2026-11-23, owner + SOL-164; amends D16)

D16's "future daily spending is not averaged in" stays the default. The person may declare a per-day "Diário previsto" (`settings.daily_estimate`, `0.01..=10000.00`) and turn it on or off (`settings.daily_estimate_on`, per user, toggling keeps the value). When on, every day after today (São Paulo, D13) and on or after the opening date takes `previsto = max(estimate − cash Diário typed that day, 0)`; the sum of previstos up to a day leaves `projected_balance`/`projected_tier` (month view, month end, `/api/forecast`, Próximos meses, RedDayAlert, Posso comprar) and never `balance`, Totals, savings, faturas or reports; it is never a row (D8). Soldi may pre-fill a suggestion (`GET /api/settings/daily-estimate-suggestion`: 3 complete months of non-card Diário ÷ days, half-even, from the opening date, none under 28 days), applied only when saved, never recomputed: a declared number, never a silent average. Card spends stay in faturas (D28). Off = D16 exactly. Convention: wherever a figure includes the estimate it says so with `EstimateNote` ("Inclui Diário previsto de R$ X/dia", a link to `/ajustes#diario-previsto`), and an estimated amount is italic with a dashed-outline icon, never a tier color. Rejected: a monthly budget spread over the remaining days (envelope budgeting), a silent trailing average (Monarch), a fake recurring entry. Detail: `docs/specs/cards/SOL-164.md`.
